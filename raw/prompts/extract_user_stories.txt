You are given the user stories of business process '%{process_id}', written by the analysts and approved by the client, together with the process passport and its use cases. The stories are final: never change, merge, split or reword them.

You will also receive RELEVANT COMPONENTS for this process (subset of the full system component catalog, with descriptions of functions and aggregates).

## TASK

Link every user story to the system components that would implement or support the functionality it asks for.

## COMPONENT LINKING

For each user story, select components based on:
- Which component's described functions match the action in the story
- Which component manages the documents, data, or artifacts mentioned
- Which component provides the service the user needs (e.g., filing → К-ПД, scheduling → К-ПЗ)

A story MUST have at least 1 component. Most stories link to 1–2 components. Only link to 3+ when the story genuinely spans multiple system capabilities.

A story whose «ХОЧУ» asks for something the System does automatically («чтобы Система автоматически…») is linked to the components that perform that automated function.

The use cases (UC) describe the same process in more detail: the task, the goal, the main scenario and the recommended functionality. Use them to understand what a story needs from the System. Do not link the use cases themselves.

Use only component IDs from RELEVANT COMPONENTS.

## OUTPUT FORMAT

Return only a JSON array with one object per story, in the order the stories are given:

[
  {"story_id": "KBP1-US-01", "component_ids": ["К-ПД"]},
  {"story_id": "KBP1-US-02", "component_ids": ["К-ПД", "К-ВДД"]}
]

- Every story_id from the list must appear exactly once; do not add other story_ids.
- Output identifiers only; do not repeat the story text.
