You are given a description of the business process with {process_id} = '%{process_id}'.

You will also receive:
- DEFINED ROLES for this process (with role_id and participant mapping)
- RELEVANT COMPONENTS for this process (subset of the full system component catalog, with descriptions of functions and aggregates)

Your task is to generate user stories that capture functional requirements from each role's perspective, and link each story to one or more system components.

## TASK

Generate user stories by analyzing process steps where each role is the actor. Each story must be:
- Directly derived from one or more process steps in the source document
- Linked to the system components that would implement or support this functionality

## GROUNDING REQUIREMENT (CRITICAL)

Every user story MUST be traceable to specific process steps.

DO NOT invent user stories based on:
- General knowledge of court processes
- Common patterns from other legal systems
- Features that "should" exist but are not documented
- Your understanding of best practices

ONLY generate user stories for:
- Actions explicitly described in the "Описание процесса (актор и описание)" column
- Activities mentioned in the "Наименование шага процесса" column
- Features suggested in the "Предложения по автоматизации шага процесса" column

If a role exists in the DEFINED ROLES but has NO corresponding steps in the process, DO NOT generate stories for that role.

## USER STORY FORMAT

Each user story follows the pattern: "Как [Персона], я хочу [Возможность], чтобы [Цель/Результат]"

The story is split into three structured fields:
- `role` — [Персона] Пользователь или роль. Определяет, для кого разрабатывается функциональность.
- `want` — [Возможность] Описание потребности пользователя или как он работает сейчас. Write as a verb phrase without "я хочу" prefix.
- `in_order_to` — [Цель/Результат] Описание ценности Возможности для Пользователя. Write as a verb phrase without "чтобы" prefix.

## DERIVATION PROCESS

For each process step:

1. Identify the actor from "Роль (актор на конкретном шаге, в т.ч. Система)" column.
2. If actor is a system/automated entity, apply System Role Transformation (see below).
3. Group related steps into coarse-grained but coherent user stories. One story typically covers 1–3 closely related steps.
4. For each story, identify which components from the RELEVANT COMPONENTS list would implement or support the described functionality.

## COMPONENT LINKING

For each user story, select components based on:
- Which component's described functions match the action in the story
- Which component manages the documents, data, or artifacts mentioned
- Which component provides the service the user needs (e.g., filing → К-ПД, scheduling → К-ПЗ)

A story MUST have at least 1 component. Most stories link to 1–2 components. Only link to 3+ when the story genuinely spans multiple system capabilities.

## RULES

### 1. Role Reference Rules

- The `role` field MUST exactly match a role name from the DEFINED ROLES.
- The `role_id` field MUST exactly match the corresponding role_id from the DEFINED ROLES.
- ONLY create stories for roles that exist in the DEFINED ROLES.

### 2. System Role Anti-Pattern

When you encounter a process step with actor "Система", "Портал", "Авто", or similar automated actors:

DO NOT assign the story to a system role.

INSTEAD, determine the human beneficiary and write the `want` field to reflect the automated action:
- `role`: "Судья"
- `want`: "чтобы поступившие документы были автоматически зарегистрированы в системе"
- `in_order_to`: "ускорить обработку входящей корреспонденции"

Process for handling System steps:

1. Examine the step's business context in "Описание процесса (актор и описание)".
2. Look at preceding and following steps to identify the human beneficiary.
3. Use your knowledge of Russian arbitration courts to determine who benefits from system steps.

### 3. Language Rules

- `want` and `in_order_to` fields MUST be in Russian.
- Use singular form (even if role name is plural).
- IDs (`story_id`, `role_id`) MUST be in Latin format.
- Maintain formal legal terminology appropriate for court processes.

### 4. Traceability Rules

- Each user story should map to 1–3 specific process steps.
- Do not create abstract or generic stories.
- Do not extrapolate beyond what is explicitly stated.
- If a process step mentions "ТБП" (Типовой бизнес-процесс), extract the intent but stay grounded in the described action.

## OUTPUT FORMAT

Output a JSON array of objects. Each object has:

1. `story_id` – String, format "%{process_id}-US-XX" (zero-padded: 01, 02, 03...).
2. `role_id` – Role identifier (MUST match role_id from DEFINED ROLES).
3. `role` – Role name (MUST match role name from DEFINED ROLES).
4. `want` – What the user wants (Russian, verb phrase, no "я хочу" prefix).
5. `in_order_to` – The business goal (Russian, verb phrase, no "чтобы" prefix).
6. `component_ids` – Array of component IDs from RELEVANT COMPONENTS (e.g., ["К-ПД", "К-МД"]).
