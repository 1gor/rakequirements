You are given a description of the business process with the {process_id} = '%{process_id}' taken from a BPMN2 diagram. It is a sequence of steps for several business actors.

You will also receive a PARTICIPANT DICTIONARY (СПРАВОЧНИК УЧАСТНИКОВ ПРОЦЕССА) — a JSON array of participant groups with member codes. You MUST link each extracted role to a specific member from this dictionary.

Focus on the "Описание процесса (актор и описание)" column to identify all participant actors in this workflow. If no such column exists, deduce participant actors (user roles) from the text.

## TASK
Extract all unique actor roles and generate a JSON array of role objects with these fields:
- `role_id`: Formatted as "%{process_id}-R-XX" (where XX is zero-padded sequential numbering: 01, 02, 03...)
- `role`: The role name in Russian (singular form)
- `description`: A concise description of this role's responsibilities within this specific process in Russian
- `participant`: An object with `code` and `name` from the PARTICIPANT DICTIONARY, linking this role to the most specific matching member

## RULES
1. **Inclusion criteria:**
   - ONLY include actors explicitly mentioned in the process steps
   - Each role must represent a human or organizational participant

2. **Exclusion criteria:**
   - DO NOT include "Система" (System) or automated actors
   - DO NOT include generic "Auto" roles

3. **Role naming:**
   - Use singular Russian nouns (e.g., "Судья" not "Судьи")
   - Transform actor mentions from the steps into proper role titles using your knowledge of Russian arbitration court and general business knowledge
   - Ensure role names are professional and appropriate for legal documentation

4. **Description requirements:**
   - Write compact, precise descriptions in Russian
   - Focus on responsibilities specific to THIS process %{process_id}

5. **Participant linkage (CRITICAL):**
   - Each role MUST be linked to the most specific member code from the PARTICIPANT DICTIONARY
   - Use your knowledge of Russian arbitration court domain to select the correct participant
   - Common mappings:
     - Истец, Ответчик, Заявитель, Должник, Кредитор → P-01.1 (Стороны по делу)
     - Третье лицо, Заинтересованное лицо → P-01.2 (Третьи лица и заинтересованные лица)
     - Председатель суда → P-02.1
     - Председатель судебного состава → P-02.2
     - Судья → P-02.3
     - Помощник судьи, Секретарь судебного заседания → P-02.4 (Сотрудник аппарата судьи)
     - Сотрудник канцелярии, Сотрудник архива, Специалист по делопроизводству → P-02.5 (Сотрудник аппарата суда)
     - Эксперт, Свидетель, Переводчик → P-03.1 (Иной участник процесса)
     - Арбитражный заседатель → P-04.1
     - Судебный примиритель → P-05.1
     - Медиатор → P-05.2
   - The `participant.code` MUST be one of the member codes from the dictionary (e.g., P-01.1, P-02.3)
   - The `participant.name` MUST match the member name from the dictionary for that code

6. **Anti-generalization rule:**
   - DO NOT create vague, generic roles like "Лица, участвующие в деле" or "Суд" — these are GROUP names from the dictionary, not specific roles
   - Always create specific roles: "Истец", "Ответчик", "Судья", etc.
   - Multiple specific roles can share the same participant code (e.g., both Истец and Ответчик map to P-01.1)

## CRITICAL: Handle System Role Anti-pattern

Sometimes you will encounter process steps with System role ("Система", "Автоматический модуль", etc.). This is weak domain modeling and must be corrected.

**NEVER create a System Role**, but do not lose steps associated with this role. Instead:

1. Look at the context of surrounding steps (preceding and following human roles)
2. Examine the `Входящие материалы` and `Исходящие материалы` columns for clues about actual responsibility
3. Use your knowledge of Russian arbitration courts to infer which human role is the actual actor in such use-cases
4. Automated routing decisions, document categorization, and procedural determinations are **judicial functions** and should be assigned to **Судья**
5. Ensure all text in the JSON output uses valid UTF-8 encoding and is in Russian (except role_id which is in Latin)

## Constraints

- ONLY create Role entities for column role values explicitly mentioned in the process steps
- DO NOT create artificial specializations or theoretical organizational roles
- Each role MUST correspond to a real actor mentioned in the process workflow, but does not need to be named exactly like the actor
- Each role MUST have a valid `participant` object with a `code` from the PARTICIPANT DICTIONARY

Output the JSON object.
